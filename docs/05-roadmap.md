# 05 — Roadmap

> Renamed: the product became Whimbrel on 2026-10-21 (`docs/superpowers/specs/2026-10-21-kestrel-to-whimbrel-rename-design.md`). This file keeps its historical wording; "Kestrel" below is the same product.

Four phases. Each has an explicit exit gate; a phase does not close until its gate is met.

> Status lines in this document were written as each milestone was worked and are not all current. The README's platform table is kept current; this file is the per-milestone record.

## Phase 1 — macOS MVP (capture · meetings · memory · chat)

Scope: FR-CAP-1…7, FR-MTG-1…7, FR-MTG-10, FR-MEM-1…4, FR-CHAT-1…3, FR-ONB-1…3, all P1 NFRs. FR-UI-1…5 (visual design/polish, see `02-functional-requirements.md`) is tracked against this phase but not gating its exit — cosmetic, not a correctness/reliability gap.

Milestones:
1. **M1.1 Capture spike** — ScreenCaptureKit audio + AX text capture proven end-to-end on macOS 14/15; TCC onboarding flow. 🚧 In progress: menu-bar app, audio spike (FR-MTG-3/10), screen-text spike with OCR fallback (FR-CAP-1…3), staged TCC onboarding (FR-ONB-1/2), and the `core/` Rust workspace skeleton (NFR-PRT-1) are implemented and build/run on this machine (macOS 26 host, deployment target 14.0). Not yet verified: a real dogfooding pass on macOS 14/15 hardware, a live meeting with contended system audio to confirm the exact FR-MTG-10 failure signature, and OCR fallback against a live Electron app. See `apps/macos/README.md` for build/run/test steps.

   **Reliable-daily-driver pass** (`docs/superpowers/specs/2026-07-25-reliable-daily-driver-design.md`) fixed a real, confirmed-not-guessed production bug found during actual dogfooding: every captured `system-audio-*.caf` file was exactly 4096 bytes — a `.caf` header with zero audio frames — across three separate real days, meaning system audio had silently captured nothing the entire time. Root-caused via log + code trace, not speculation, and fixed alongside a calendar-trigger dry run and a rough-edges sweep of crash-class bugs found in the same session (including the capture-toggle SIGSEGV mentioned below under FR-UI-4). This directly narrows the "live meeting with contended system audio" verification gap above, though full hands-on dogfooding is still blocked by R10.

   FR-CAP-4 (per-app exclusion) landed too, alongside a broader UI restructuring: `apps/macos` now has a real native Settings scene (⌘,, `SettingsView.swift`) replacing the ad-hoc mix of a standalone "Permissions" window and settings stacked into the debug window. Settings is config-only (Permissions, Capture exclusions, Meetings auto-start/lead-time, Transcription model path, Retention windows, Diagnostics); the debug window (`ControlWindowView.swift`) is now just live status and one-shot actions (capture toggle, current/upcoming meetings, "Transcribe Latest Meeting") — matching the separation the real Littlebird app's UI uses. `CaptureExclusions` (new `Support/CaptureExclusions.swift`) is checked in `ScreenTextCaptureService` *before* any Accessibility/OCR extraction happens, not filtered out after — excluded apps' content is never walked, not just never stored. Currently lists only running apps (no full installed-apps enumeration) and has no pre-seeded defaults or per-URL-pattern matching yet — both still open against FR-CAP-4's full scope. Whisper model path is also user-configurable now (Settings → Transcription, `NSOpenPanel`-based picker) instead of hardcoded.

   The app is named **Kestrel** now, not "LBCaptureSpike" — that was always a placeholder chosen only to dodge the bundle-ID/product-name collision with the real Littlebird app during signing, and it stuck around longer than intended. `apps/macos/Littlebird/` → `apps/macos/Kestrel/`, product name/bundle ID (`com.mpointer.kestrel`)/scheme/Xcode project/all user-visible UI text updated to match; see open question #7 in `06-risks-open-questions.md`. Also dropped `LSUIElement` — the app now shows a Dock icon (no custom artwork yet, so it's Xcode's default placeholder for now). Internal identifiers that aren't user-facing were deliberately left alone: the Rust core's library name (`littlebird_core`), the on-disk spike data path (`~/Library/Application Support/littlebird/spike/`, to avoid orphaning already-captured test data), and the `littlebird-clone` repo name itself.

   **This entry's own description of the debug window is now superseded.** Direct user frustration — the app auto-opening into a window literally titled "Kestrel (Debug)," and meeting details (a `.sheet`) having no window chrome — drove a real restructure (`docs/superpowers/specs/2026-07-28-primary-window-restructure-design.md`). `ControlWindowView.swift` is deleted entirely; Timeline (`Window("Kestrel", id: "timeline")`) is now the app's primary, auto-opening window, carrying everything the debug window did (capture toggle/status, the in-meeting notes pad). Meeting details are a real `WindowGroup(id: "meeting-detail", for: Int64.self)` scene now — one independent, fully-chrome'd window per meeting, fetching fresh data via a new `Store::get_meeting(id:)` accessor rather than a value passed in at open time (this also incidentally fixed Timeline showing a stale summary after a regenerate-and-close). One real bug surfaced live after merge, not caught by any review: "Transcribe Latest Meeting" and Settings access had moved to the menu-bar popover, which turned out to be genuinely unreliable in practice (Control Center hosting/menu-bar overflow hid the status item entirely on the test machine) — exactly the risk the original debug window's own doc comment had called out as the reason it existed independently of the menu bar in the first place. Fixed by giving Timeline (always open) its own copies of both controls rather than depending solely on the menu bar. **Explicitly deferred, each needing its own future brainstorm:** Routines (Phase 2, needs a scheduler/heartbeat subsystem that doesn't exist yet) and multi-tab chat (a real feature on top of Ask mode, not a window-structure change) were both raised during this work and intentionally split out.
2. **M1.2 Memory pipeline** — ingest → SQLite/sqlite-vec → hybrid search → timeline UI. 🚧 Groundwork in progress: `core/memory` has a SQLite (WAL) store for `capture_item` with FTS5 keyword search, timeline-by-range queries (FR-MEM-1), and time/app-scoped hard-delete (FR-MEM-4 basic version); `core/ingest` normalizes text, simhash-dedupes (FR-CAP-6), chunks, and reads the macOS spike's `screen-text.jsonl` straight into the store. sqlite-vec is now wired in too (pinned to 0.1.9 after its 0.1.10-alpha.* releases failed to build here — R11): a `vec0` table ~~plus a deterministic hashing-trick placeholder embedding (not a real semantic model yet, see `core/memory`'s module docs)~~ **now backed by a real local model** prove nearest-neighbor search works end to end via `search_semantic`. `core/ffi` exposes open/close a store, ingest a JSONL file, keyword search, and semantic search over the C-ABI (JSON-in/JSON-out, per the small-and-message-based FFI approach in R9) rather than just the version-string stub from M1.1. 18 unit tests passing across `memory`/`ingest`/`ffi`. The Swift shell now actually links and calls into it — `apps/macos` builds `core/ffi` as a static library, imports it via a bridging header, and `CoreBridge.swift` wraps the C-ABI in a small Swift API. A `CoreSelfTest` runs automatically when the debug window opens: ingests a fixture (and the real `screen-text.jsonl` if present), runs both search paths, and writes a pass/fail report to `~/Library/Application Support/littlebird/spike/core-selftest.txt`. Independently verified via a standalone Swift script linked against the same static library (open → ingest → keyword search → semantic search → recent → close, all correct) without needing the full GUI app. A `TimelineView` (SwiftUI) now exists too: a Recent/Keyword/Semantic picker over a live `List` of results, opened via a "Timeline…" button in the debug window, backed by a store shared across the app (`AppState.coreStore`) rather than a one-off connection per view. M1.2's explicit scope (ingest → SQLite/sqlite-vec → hybrid search → timeline UI) is now implemented end to end, with one remaining caveat: ~~the embedding is a placeholder (not a real semantic model — candle/ONNX still needed)~~ **LB0-1 replaced this 2026-07-31**: `core/memory` now embeds via a real local `candle` + `sentence-transformers/all-MiniLM-L6-v2` model (384-dim, masked mean pooling, `accelerate`-accelerated), bundled straight into the signed `.app` (same XcodeGen folder-reference-resource pattern M2.1's Calendar connector proved) rather than requiring a manual download — see `docs/superpowers/specs/2026-07-31-real-local-embedding-model-design.md`. Existing rows migrate incrementally in the background (`Store::reindex_batch`, one row per turn via a throttled Swift loop, self-healing across restarts via a persisted `kv_meta` cursor) rather than blocking app launch — real per-row embed time on this machine is ~150-220ms for `capture_item`-length text, and the real local database has 80,939 such rows, so an eager migration would have taken hours of blocked launch time. Every embedding failure (missing model, load error, inference error) degrades gracefully throughout — capture, keyword search, and `open()` itself never fail because of it, only semantic-search completeness for not-yet-migrated rows. Three real bugs were found and fixed during implementation, none by mere code review — all via actual reproduction against real data: (1) `reindex_batch` silently losing rows forever if the model was ever unavailable at all (fixed: fail fast, don't advance the cursor); (2) `sqlite-vec`'s `vec0` virtual table doesn't implement SQLite's `INSERT OR REPLACE` conflict resolution, so re-indexing a row that already had a vector entry — which happens routinely via ordinary live capture — threw a permanent UNIQUE-constraint error (fixed: explicit delete-then-insert); (3) the persisted reindex cursor's read-back parsing silently defaulted to 0 for a `"capture_item:<N>"` value, so real Swift usage (`maxRows: 1`) reprocessed row 1 forever instead of ever advancing — found only by the final whole-branch review, since the only prior test used a `max_rows` large enough to reach a different, unaffected code path in a single call. Known, deliberate limitation, not yet closed: once the one-time backlog drain reaches its terminal "done" state, a row whose embedding failed at insert time for an unrelated reason (the model was already loaded, but that one call somehow failed) can never be backfilled — narrow edge case given the model ships bundled, logged as a follow-up rather than blocking this pass. And there's still essentially no real capture data to browse yet since M1.1's TCC blocker (R10) hasn't cleared. FR-MEM-3 (end-of-day digest) is done too, once the LLM router landed: `llm::generate_daily_digest(client, items)` — skips the model call entirely (no cost) if there were no items in the time range — exposed over FFI as `littlebird_llm_daily_digest` and wired into `TimelineView` as a "Digest" mode ("Generate Today's Digest" button, computes local-timezone day boundaries, shows summary + open loops). Verified against real Ollama, including through the full Swift↔Rust stack via the standalone verification script.

   **Information-gathering architecture (`docs/09-information-gathering-design.md`) started 2026-08-07, three slices shipped since.** Doc 09 proposes four layers (L0 raw events → L1 items → L2 episodes/threads → L3 knowledge) on top of the flat `capture_item`/`transcript_segment` model above, so background distillation doesn't need to re-crawl raw data on every chat/routine call. **Items-table migration** (L1, `docs/superpowers/specs/2026-08-07-items-schema-migration-design.md` + two follow-on specs) landed a unified `items` table (dual-written from `capture_item`/`transcript_segment`/calendar events, with a `(kind, source, external_id)` dedup index that later work reuses directly) and rewired existing reads onto it — no user-visible behavior change, pure groundwork. **Job queue + T1 worker** (L2 Slice A, `docs/superpowers/specs/2026-08-07-job-queue-design.md`) added a generic `jobs` table + `Store::run_jobs_batch`, driven by a new AC-power/idle-gated Swift loop replacing the old unconditional reindex timer, and migrated the existing embedding backfill onto it as the first job type. **Episodes** (L2 Slice B, `docs/superpowers/specs/2026-08-12-l2-episodes-design.md`) added a second job type, `episode_segment`, that groups `items` (kind='capture') rows into contiguous same-app activity windows (app-switch/idle-gap boundaries, with a blip-merge pass for rapid alt-tabbing) and a third, `episode_summarize`, that turns each into a 2-3 sentence summary via a local Ollama call — the first real T1 (local-batch-inference) work doc 09 §5 called for. The final whole-branch review caught two Critical bugs neither per-task review saw (a NULL-field episode that could permanently jam the summarize queue forever, and no recovery path for a job stranded `'running'` by a crash mid-Ollama-call) plus a genuine data-integrity gap discovered only by checking the real dogfooding database directly (the cursor redesign needed a migration or it would have duplicated ~155 already-segmented episodes on next launch) — all fixed before merge. No UI surfaces episodes yet; this slice is backend infrastructure only, same as Slice A was for the job queue. Threads (doc 09's other L2 object) are explicitly deferred — they need the connector `sync` capability below, which didn't exist until the next item. **Threads shipped 2026-08-14** (`docs/superpowers/specs/2026-08-14-thread-distillation-design.md`), MVP-scoped: a `threads` table plus `thread_state_sync` (groups Gmail `items` into threads, computes a rule-based `status` — `waiting_on_me | waiting_on_them | resolved | fyi` — via a deterministic direction/CC/staleness rule, no LLM) and `thread_summarize` (incrementally updates a rolling summary via local Ollama, feeding only new messages since the last update plus the prior summary — never re-summarizing a long thread from scratch). `asks_of_me[]`/`commitments_by_me[]` extraction and the two-stage priority classifier (blocked on sender-rank/L3 profile data that doesn't exist yet) are deferred to later slices. A genuine spec ambiguity surfaced mid-implementation — whether `fyi` should freeze at a thread's first message or re-evaluate as new messages arrive — resolved by the user toward re-evaluation (a thread permanently exits `fyi` the moment it's ever directly addressed). The final whole-branch review caught two Critical bugs neither per-task review could see: `thread_state_sync`'s own job was never revived mid-session (only at app restart), so the feature would have gone stale after the first catch-up in any long-running session; and an empty `thread_summarize` claim could overwrite a good rolling summary with model noise while resetting its provenance cursor to 0, breaking the "never re-summarize from scratch" guarantee that's the point of the whole design. Both fixed and re-reviewed before merge. Merged `2321ca8..243fef1`. No UI surfaces threads yet, matching Episodes' own backend-only precedent.
3. **M1.3 Meetings** — calendar + detection triggers, whisper.cpp transcription, note blending, summaries. 🚧 Transcription groundwork started: `core/transcribe` has a real, working whisper.cpp integration via `whisper-rs` (FR-MTG-4) — `Transcriber::load` + `transcribe_wav` (16kHz i16 PCM, mono or stereo-downmixed). Verified end to end against real audio, not just compiled-but-untested: macOS's `say` synthesized "The quick brown fox jumps over the lazy dog," and whisper.cpp's tiny.en model correctly transcribed it back. Model file (~75MB) isn't checked into git — see `core/transcribe/README.md`. Real per-speaker diarization on the system-audio channel now exists via the `core/diarize` crate (`sherpa-onnx`): mic stays "Me", and system audio gets "Speaker N" labels when diarization models are configured, degrading to "Others" otherwise. Note blending (FR-MTG-5) is implemented too: `llm::summarize_meeting(client, notes, transcript)` blends rough notes with a transcript into a structured `MeetingSummary { tldr, decisions, action_items, open_questions }`, robust to models wrapping their JSON response in markdown fences or preamble text. Deliberately kept free of a structural dependency on `transcribe` (plain `&str` in, so `llm` doesn't need whisper-rs/CMake) — but the **full real pipeline** was verified via a one-off scratch harness: macOS `say` synthesizes meeting audio → `Transcriber` transcribes it (word-for-word correct) → `summarize_meeting` (real Ollama call) produces an accurate summary with the right decisions and open questions. 11 unit tests run by default in `llm` (up from 7), 3 requiring a live Ollama server. Transcription is wired into `apps/macos` now too: `core/ffi` finally does take `transcribe` as a dependency (justified now that something calls it — `littlebird_transcribe_wav(model_path, wav_path)`, a fresh-load-per-call, JSON-array-of-segments FFI function), and `apps/macos` gained `Littlebird/Support/AudioConversion.swift` (AVAudioConverter-based, converts captured `.caf` audio — whatever rate/format `AudioCaptureService` wrote it in — to the 16kHz mono i16 WAV `transcribe_wav` requires, since that crate deliberately doesn't resample) and `Littlebird/Support/TranscriptionService.swift` (finds the most recent system-audio/mic-audio pair, transcribes each channel separately — mic="Me", system audio gets real per-speaker labels via the new `core/diarize` crate when models are present, falling back to "Others" when they aren't — merges chronologically, writes `transcript-<timestamp>.txt`). A "Transcribe Latest Meeting" button in the debug window drives it. Needed two build-config fixes discovered by actually linking whisper.cpp/ggml into the app for the first time: `OTHER_LDFLAGS` needed `-lc++` (C++ runtime, nothing else in this Swift/C project pulled it in), and cmake became a real build prerequisite (documented in `apps/macos/README.md`). Verified genuinely end-to-end, not just "it compiles": a standalone Swift harness (same no-GUI-needed pattern used for the core-bridge verification) synthesized a 48kHz stereo Float32 `.caf` via macOS `say` — matching real captured-audio shape, not a pre-made 16kHz fixture — ran it through the actual `AudioConversion.swift` production code, then the real FFI call, and got back a byte-perfect transcript.

   **Meeting transcripts are searchable now too** (FR-MEM-1/FR-MEM-2/FR-CHAT-1 follow-on) — closing a real gap surfaced by hands-on use: Ask/Keyword/Semantic modes previously only ever indexed screen-text captures, never meeting content, despite this doc's own data model always having speced a `transcript_segment` table for exactly that (never built until now). `core/memory` gained the table (FTS5 + sqlite-vec, mirroring `capture_item`'s existing pattern), populated from each transcription's already-labeled per-line data right after transcription completes. Citations are now a tagged type (`{"kind":"capture"|"transcript","id":...}` — `core/llm::ContextItemRef`) rather than a bare integer, since `capture_item`/`transcript_segment` ids are independent sequences that can collide. Keyword/Semantic browsing and Ask-mode retrieval both merge results from both tables now (captures-then-transcripts, not re-sorted across the two different search engines' incomparable rank/distance scores). Deleting a meeting (both the single-meeting action and the FR-MEM-4 retention sweep) cascades to its transcript segments too. Ingestion is forward-only, though — segments are only populated for meetings transcribed after this feature landed, and there's no backfill path, so meetings recorded/transcribed before this merge have no `transcript_segment` rows and stay unreachable via Ask/Keyword/Semantic. Their transcript file on disk and the meeting detail view are unaffected; only the searchable index is missing.

   Calendar triggers (FR-MTG-1) are implemented now too: `core/memory` gained a `meeting` table (id, device_id, start/end ts, title, attendees, trigger `calendar`|`detected`, audio_path, status `scheduled`|`recording`|`completed`|`cancelled` — matching the architecture doc's data model) with `insert_meeting`/`update_meeting_status`/`complete_meeting`/`recent_meetings`, exposed over `core/ffi` the usual JSON-in/JSON-out way. On the Swift side: `MeetingDetection.swift` is a pure, EventKit-free function that recognizes Zoom/Google Meet/Teams/Webex links in an event's location, notes, or URL field — verified standalone (10 cases: each provider, trailing-punctuation trimming, location-takes-priority-over-notes, no-link-found) without needing Calendar access or any TCC grant. `CalendarService.swift` wraps `EKEventStore`, polls a 2-hour lookahead window every 60s, and filters to events that qualify per FR-MTG-1 ("conferencing link or ≥1 other attendee"). `MeetingTriggerService.swift` watches those qualifying meetings and, at a configurable lead time (default 1 minute, matching the spec), either posts a local notification + in-app "Start Recording / Dismiss" prompt, or — if the user has enabled auto-start — starts capture directly; each event is only acted on once per app run (in-memory, keyed by `EKEvent.eventIdentifier`). Accepting a prompt (or auto-start firing) now inserts a `meeting` row and, when capture stops, completes it with the actual end time and the captured audio file path — so a calendar-triggered session is a real persisted record, not just an ephemeral toggle. Calendar and Notifications were added as two more staged onboarding permissions (FR-ONB-1's full five-permission list is implemented now), and the debug window shows upcoming qualifying meetings, the pending-prompt banner, and auto-start/lead-time controls.

   FR-MTG-2 (the audio/app heuristic — detecting a meeting with no calendar entry) is implemented now too: `MeetingHeuristicDetector.swift` polls (every 5s) for a known meeting app (Zoom/Teams/Slack/Webex/FaceTime) running alongside active mic + system audio (`AudioDeviceActivity.swift`, via `AudioObjectGetPropertyData`/`kAudioDevicePropertyDeviceIsRunningSomewhere` — no capture entitlement needed, just a device-in-use query), firing after 2 consecutive matches (~10s, under FR-MTG-2's 30s budget), deduped per bundle ID for the app's lifetime. `QualifyingMeeting` gained a `source` (`.calendar`/`.detected`) so the prompt banner, notification text, and the persisted `meeting.trigger` all reflect which path fired; toggleable in Settings → Meetings, opt-out default since it's prompt-only. ~~Known gap, left deliberately unimplemented and documented in the detector's doc comment: a meeting joined from a browser tab (e.g. Meet) isn't covered — that would need an Accessibility-tree walk independent of `ScreenTextCaptureService`, which only runs when capture is already on.~~ **LB0-3 closed part of this 2026-08-01** (`docs/superpowers/specs/2026-07-31-meeting-end-and-google-meet-detection-design.md`): `BrowserMeetingCheck.swift`, a lightweight, bounded-depth AX check (not the full `ScreenTextCaptureService`/`AXTextWalker.extract()` text-walk, which still only runs once capture is on), now recognizes a `meet.google.com` URL in the frontmost browser's focused window, independent of capture state, and `MeetingEndDetector` gained an equivalent to native apps' "app quit" signal for it — the tracked window is re-checked on every poll and the meeting ends (debounced 15s, to survive an ordinary brief tab-switch) once the tab genuinely closes or navigates away. **Verified live against a real running browser, not just unit-tested** (this class of AX code isn't meaningfully mockable, matching this codebase's existing zero-AX-test convention): Safari works cleanly — positive match, navigated-away, and tab-closed cases all confirmed. **Chrome does not work, and this is a real, root-caused gap, not an oversight**: Chromium's renderer accessibility tree is lazily activated, and nothing triggers that activation under ordinary polling — confirmed via ~230 seconds of continuous unaided-polling attempts across two separate fresh Chrome process lifetimes, 0 successes. The only thing that activates it is explicitly calling `AXUIElementSetAttributeValue(..., "AXEnhancedUserInterface", true)` on Chrome's process — a real side-effecting call (mutates a third-party process's accessibility state, with a known CPU cost for that Chrome instance) whose lifecycle (call once or every poll? undo it when Kestrel quits, so Chrome doesn't stay in full-accessibility mode forever?) is a real design decision, deliberately deferred rather than bundled into this pass. Shipping Safari-only for now; a future pass can pick up Chrome support with that specific activation question decided up front. Other browsers (Arc/Edge/Firefox) and other in-browser meeting platforms remain out of scope, same as this detector's existing "most common cases, not exhaustive" tolerance for its native-app bundle-ID list. Teams/Webex bundle IDs are best-effort, not verified against real installs. Cross-relaunch dedup for "already prompted for this meeting" (both calendar and heuristic paths) is in-memory only — restarting the app mid-lead-window could re-prompt for the same event; low-risk enough to accept for now given the app is meant to run continuously. The heuristic detector's per-bundle-ID dedup set is now cleared once no meeting app is running (rather than staying dirty for the app's whole lifetime), so the same app quitting and later starting a genuinely new meeting re-qualifies correctly — one incremental fix, not a full rework of the in-memory-only limitation above. Not yet verified: an actual live Calendar TCC grant and a real qualifying meeting firing the prompt/auto-start flow end to end, and the heuristic detector against a real Zoom/FaceTime call (blocked on hands-on testing, same as the rest of M1.3/M1.1's manual test script).

   **Floating meeting-alert panel** (`docs/superpowers/specs/2026-07-27-meeting-alert-panel-design.md`) replaced the two weak, disconnected trigger surfaces above (a generic system notification, and an in-app banner only visible if the popover/debug window happened to be open) with a single floating panel matching the real Littlebird app's presentation: accent bar, app icon, and inline "Start Recording" actions, shown for both calendar and detected triggers alike. This is a genuine behavior addition, not just a restyle: when auto-start is enabled, the panel now shows a 10-second countdown before auto-starting (with an early-override option) — previously auto-start fired with zero visual feedback at all, capture just silently began.

   **Meeting lifecycle + at-a-glance dashboard** (`docs/superpowers/specs/2026-07-27-meeting-lifecycle-and-dashboard-design.md`) closes out FR-MTG-5 for real, past just note-blending. Meeting end is now detected automatically via five heuristics, in priority order (see `MeetingEndDetector.swift`'s own doc comment): the meeting app quitting (detected/non-calendar meetings only); for a browser-detected meeting, its Meet tab being sustainedly gone — closed, or navigated away from and not back — debounced 15s so an ordinary brief tab switch doesn't end a still-live meeting; a hard ceiling 10 minutes past a calendar meeting's own scheduled end time, firing unconditionally regardless of audio; an absolute 4-hour maximum recording duration as a last-resort safety net for any meeting; and sustained real audio-content silence (not just "is a capture device running," an earlier version of this got that distinction wrong and it never fired) — 60 seconds normally, 15 seconds once already past a scheduled end time, not just a manual toggle. An in-meeting notes pad captures rough notes live during capture. Transcription and summarization now run automatically in the background the moment a meeting ends, including for long real meetings: transcripts past a model's context window are chunked and map-reduced into one final summary rather than silently failing (a real, confirmed production bug from a live 55-minute meeting, root-caused and fixed, not a hypothetical). A new meeting detail view (tap a Timeline row) shows the summary, notes, and full transcript, degrading gracefully through every in-progress state. A new at-a-glance dashboard panel shows upcoming qualifying meetings with working "Join" buttons and a cached daily digest (FR-MEM-3) that doesn't re-trigger an LLM call on every reopen. ~~Known gap, still open: the audio-silence heuristic's amplitude threshold has not been confirmed correct against a real quiet room — a live test showed auto-end-detection not firing despite genuine silence and being past a meeting's scheduled end; diagnostic logging (peak amplitude per channel) was added afterward but hasn't yet been re-tested with real data.~~ **Shipped 2026-08-06**: `AudioCaptureService.silenceAmplitudeThreshold` recalibrated from 0.01 to 0.1, based on two independent live measurements (a standalone probe and a real production capture) both showing ambient/quiet-room peaks of 0.044-0.075 misclassified as audible under the old value. See `docs/superpowers/specs/2026-08-06-silence-threshold-recalibration-design.md`.

   **Model-selectable summary regeneration** (`docs/superpowers/specs/2026-07-27-model-selectable-summary-regen-design.md`) lets a user regenerate a meeting's summary from its full transcript using any configured provider/model — Ollama, Anthropic, or OpenAI — from the meeting detail view, reusing the per-conversation provider+model picker built for Timeline's Ask/Digest modes (see M1.4 below). The detail view shows which provider/model produced the currently-displayed summary. Verified against a real live meeting transcript with a real Anthropic call, which surfaced and fixed a genuine pre-existing bug: `AnthropicClient`'s hardcoded 1024-token response cap was too small for a real summary, truncating the JSON response before its closing brace; raised to 4096.

   **Per-chunk spend-cap governance** (`docs/superpowers/specs/2026-07-27-meeting-summary-spend-cap-governance-design.md`) closes a real gap the map-reduce summarization fix above had left: the spend cap was checked once and usage logged once per whole summarize-meeting call, even though a long meeting's map-reduce can make many real LLM calls internally — meaning partial spend on a mid-operation failure was invisible, and a cap hit mid-operation was never re-checked before a costly provider-failover restart. `core/ffi` now orchestrates the chunking loop itself (`summarize_meeting_governed`) and checks the cap + logs usage after every actual call, not once for the whole operation; a real bug found along the way (a transcript that's a single unsplittable line over budget was wrongly taking the no-chunking fast path) got fixed too. A test proving the fix's actual headline behavior — a cap tripping mid-operation from real accumulated cost, not just a pre-check — was added after a whole-branch review caught that the first two tests used the free local Ollama provider and so never exercised real cost accumulation at all.

   **Diarization quality pass** (`docs/superpowers/specs/2026-07-31-diarization-quality-design.md`) tightened transcript accuracy and usability. Mic bleed-through filtering (`TranscriptPostProcessing.filterBleedThrough`, `apps/macos/Kestrel/Support/TranscriptPostProcessing.swift`) now drops "Me" channel lines that are near-duplicates of system-audio content — when recording via speakers instead of headphones, the mic physically captures meeting audio and whisper transcribes it a second time on the wrong channel. Filtering uses Jaccard word-overlap similarity (threshold 0.35, validated against 712-segment real fixture, every match in [0.35, 0.6) manually confirmed as genuine bleed, sub-0.3 overwhelmingly coincidental), a 150-centisecond time window (validated against real bleed-through pairs landing 0-130cs apart), and a 4-word minimum (to avoid filler-word collision false positives like "okay" matching independently). Same-speaker segment merging (`TranscriptPostProcessing.mergeAdjacentSameSpeaker`) combines choppy one/two-word fragments from the same speaker into continuous lines when consecutive same-speaker lines fall within 200cs of each other, improving readability (validated against a real 712-segment meeting transcript: of 103 consecutive same-speaker segment pairs, only 29% fell within the original 100cs tolerance, median gap 220cs; 200cs catches 45% without risking merges across genuinely separate turns). Integration test against real Mac-B fixture pattern confirms the two transforms work together end-to-end: the shape "Speaker 1 says X, then Y (bled as Me), then Z" correctly reduces to one continuous "Speaker 1 says X, Y, Z" after filtering and merging. All 13 Swift tests pass including direct validations of both fuzzy and exact bleed matching, filler-word preservation, and timing-gap boundaries (including a chained-gap regression test added in the final-review pass, discriminating the correct consecutive-gap merge semantics from an earlier anchored-window bug). Diarization label-matching widening (`core/diarize`'s `label_speakers`) now matches transcript segments to speaker segments using nearest-within-tolerance logic instead of exact-midpoint-only, reducing how often a transcript segment falls back to the generic "Others" label on a close boundary miss rather than a genuine unmatched segment (oversegmentation itself is `DEFAULT_CLUSTERING_THRESHOLD`'s concern, a separate constant deliberately left untouched here — see Task 6's entry). - **Meeting snapshots (FR-MTG-11), requested 2026-10-22; implemented, pending manual pass** (checklist: `docs/superpowers/plans/2026-10-22-meeting-snapshots-manual-pass.md`; design: `docs/superpowers/specs/2026-10-22-meeting-snapshots-design.md`). Granola captures periodic screenshots during a meeting so slides and other shared visuals are kept with the notes. Kestrel should do the same: sample the shared screen or meeting window on an interval, drop near-duplicate frames, store the kept stills against the meeting timeline, OCR them into search, and show them in meeting detail (and optionally pass slide text to the summary). Building blocks already exist: ScreenCaptureKit is used for meeting audio and `OCRFallback.swift` already grabs window images. Open questions for the design pass: which window or display to sample when several are shared, interval and change-detection threshold, storage size and encryption, whether the summary prompt sees slide text, Windows parity, and sync (images are large; content sync today carries no blobs).
