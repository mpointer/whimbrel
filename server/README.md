# server

Cloudflare Worker: verifies Google ID tokens against a fail-closed sign-in allowlist, maintains a control-plane account/device registry, provisions one isolated Turso database per account, and mints device tokens scoped to only that account's database via `POST /v1/auth/google`. The wrapped-group-key handoff (KV store-and-forward) is implemented but not yet wired into any route — that lands with the full enrollment-flow plan. Not a data-plane component — sync payload data (`capture_item`/`meeting`/`transcript_segment`/`summary`) goes straight from a device to its account's own Turso database once the device holds a token from this Worker. See `docs/superpowers/specs/2026-07-29-multi-device-sync-accounts-design.md` for the design and `docs/superpowers/plans/2026-07-29-sync-auth-worker.md` / `docs/superpowers/plans/2026-07-29-sync-worker-account-isolation.md` for what's implemented so far.

## Before deploying

Deployment variables, Turso and OAuth setup, and pointing the apps at your own relay: [docs/self-hosting.md](../docs/self-hosting.md).

- `SCHEMA_SQL` (in `src/accounts.ts`) uses `CREATE TABLE IF NOT EXISTS` — it will not retroactively add new columns to an already-created control-plane table. Run it once against a fresh database; if the control-plane database already exists from an earlier version of this Worker, apply the missing columns manually first.
- Run `migrations/0002_cloud_plan.sql` against the control-plane database before deploying the version that adds the Cloud plan: its account `SELECT` names the new `plan*` and `stripe_*` columns and fails without them. It is one `BEGIN; … COMMIT;` transaction; run it as one script that stops at the first error. If it still fails partway, run `PRAGMA table_info(account);`, then run only the `ALTER TABLE` lines whose column is missing, plus the `CREATE TABLE IF NOT EXISTS stripe_event` statement.
- `STRIPE_PORTAL_CONFIGURATION` (a Worker variable, optional, not a secret) is the `bpc_…` id of a Stripe Billing Portal configuration that offers only Whimbrel's prices. The Stripe account is shared with another product, so without it the default portal could offer that product's plans. Unset means Stripe's default portal. Set it before launch. The webhook acts on a subscription only when one of its items carries `STRIPE_PRICE_MONTHLY` or `STRIPE_PRICE_YEARLY`, or when its `metadata.account_id` names a Whimbrel account; it ignores every other subscription and logs one line (id and status). Never retire a price that still has live subscriptions: the metadata keeps their renewals landing only while the account exists.
- Stripe setup before launch, in the Stripe Dashboard:
  - Billing → Subscriptions and emails → "If all retries for a payment fail": choose cancel the subscription (or mark it unpaid). Either ends Cloud; leaving it past due keeps Cloud on.
  - Webhook endpoint `https://<worker>/v1/billing/webhook` with these events: `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`, `invoice.payment_failed`.
  - `STRIPE_PORTAL_CONFIGURATION` set (see above).
- A Whimbrel Cloud subscription whose account is deleted or being deleted (a Checkout finished after the deletion, say) is cancelled by the webhook at once, with no refund, and an email to the alert address asks you to refund by hand. The account's own stored subscription is left to the deletion below.
- Deleting an account (self-serve, or the cron finishing a deletion) cancels its stored Stripe subscription at once (also an unpaid or paused one that ended the plan; one Stripe already ended is left alone): no proration, no automatic refund. If Stripe refuses, or `STRIPE_SECRET_KEY` is unset, the deletion still goes ahead and an email to the alert address (`hello@whimbrelapp.com`, needs `RESEND_API_KEY`) asks you to cancel by hand; the log carries the ids only. Only the stored subscription id is touched, never a search by customer email.
- `TURSO_DB_GROUP` (a Worker variable; `wrangler.jsonc` sets `keep_vars` and carries none of the deployment values) must name a Turso group that already exists (`turso group create <name>`) — this Worker does not create it.
- Every account gets its own Turso database (`whimbrel-sync-<uuid>`), created on that account's first sign-in via Turso's Platform API. The free tier supports up to 100 databases.
- `POST /v1/devices` and `POST /v1/devices/:id/approve` are for the native app's device-approval flow — there is no native caller yet as of this plan; `core/ffi`'s crypto bindings and the native enrollment UI are separate, later plans.
- `GOOGLE_IOS_CLIENT_ID` (a Worker variable, unset by default) is the iOS app's Google OAuth client ID, accepted as a second ID-token audience alongside `GOOGLE_CLIENT_ID`. Empty/unset means iOS tokens are rejected. Production needs this set and a deploy; the `ALLOWED_GOOGLE_EMAILS` allowlist still applies.
- `GOOGLE_ANDROID_CLIENT_ID` (a Worker variable, unset by default) is the Android app's Web OAuth client ID, accepted as a third ID-token audience. Empty/unset means Android tokens are rejected. Android is a phone audience exactly like iOS: it can't be an account's first device and can't start a reset.
